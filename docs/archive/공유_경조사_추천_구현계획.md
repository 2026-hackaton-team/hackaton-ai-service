# 공유 경조사 추천 구현계획

> 작성일: 2026-10-31
>
> 상태: **작성 당시 계획 보존**. 공유 소식 등록·관계별 추천·철회와 관련 회귀 검사는 이후 구현했다. 실제 시연 순서와 확인한 범위는 `docs/PRESENTATION_DEMO.md`를 따른다. 아래의 현재 상태와 실행 계획은 작성 당시를 기준으로 한다.

## 1. 목표와 범위

사용자가 직접 입력하지 않아도 다른 가상 계정이 공유한 경조사를 친구·친구의 친구·확인된 직장동료 관계를 근거로 추천한다. 같은 행사가 이미 등록된 것으로 식별되는 경우에는 추천 목록에서 제외한다. 추천 이유와 실제로 확인된 공개 조건을 함께 보여주고, 행사 당사자와 공유자를 구분한다.

첫 구현은 **합성 데이터와 가상 계정을 사용하는 로컬 시연**으로 한정한다. 핵심 완료 기준은 다음 흐름이다.

1. 가상 계정 A가 앱에서 가상 경조사를 등록하고 공유 범위를 선택한다.
2. 가상 계정 B가 자신의 일정 화면에서 공유 조건을 통과한 소식과 추천 이유를 확인한다.
3. A가 공유를 철회하면 B의 다음 목록·상세 조회에서 해당 소식이 제외된다.
4. 직장동료 소식은 동료 계정과 인맥이 가상 데이터에서 명시적으로 연결되고, 행사 관련 인물의 사용이 허용된 경우에만 그렇게 표시한다.

가상 계정 선택은 운영 인증이 아니므로 실제 개인정보를 넣거나 서버를 외부에 공개하는 용도로 사용하지 않는다. 공유 권한 확인 표시는 시연용 자기 확인이며 실제 권리나 동의를 검증하지 않는다.

**이번 범위에서 제외:** 외부 메신저 자동 수집·연동, 회사 인증과 모임 관리, 실제 회원 인증, 추천 모델 학습, 새 공유 소식의 AI 상담 연결, 추천 소식의 개인 일정 복사, 푸시 알림. 기존 AI 상담과 개인 일정 기능은 유지한다. 후속 단계의 의존성은 10절에 정리한다.

## 2. 현재 코드에서 확인한 상태

| 항목 | 현재 상태 | 구현 시 영향 |

추가로 기존 `notice` 응답에는 공유자 이름을 숨겨도 `publisher_user_id`가 포함된다. 가상 계정 목록과 결합하면 이름을 다시 알 수 있으므로, 새 API뿐 아니라 기존 부고 API의 응답에서도 내부 공유자 ID를 제거해야 한다. 제목 등 다른 내용으로 유추될 가능성까지 없어진다는 뜻은 아니다.

## 3. 사용자 흐름

### 3.1 공유자

1. 일정 화면에서 **공유 경조사 등록**을 선택한다. 기존 개인 일정 등록 버튼과 구분한다.
2. 행사 유형, 제목, 시작일·종료일, 선택 항목인 지역·장소를 입력한다.
3. 공개 범위를 `나만 보기`, `직접 친구`, `직접 친구와 친구의 친구` 중에서 고른다. 기본값은 `나만 보기`다.
4. 각 관계의 참석 허용 여부를 `허용`, `불허`, `미확인` 중에서 명시한다. 미선택 기본값은 `미확인`이다.
5. 범위를 넓히는 경우 공유 권한을 확인했다는 시연용 항목을 선택한다. 체크가 없으면 공유 범위로 저장하지 않는다.
6. 소식의 관련 인물이 자기 자신인지, 부고에서는 본인이 상주인지 선택할 수 있다. 해당 관계를 추천 이유로 이용하도록 별도로 허용하고 공유자 이름 공개도 허용한 경우에만 수신자의 확인된 동료 연결과 비교한다. 제3자를 임의의 계정 ID로 연결하는 입력은 제공하지 않는다.
7. 저장 후 `내가 공유한 소식`에서 자신의 소식을 확인하고 공유를 철회할 수 있다. 철회는 소식을 비공개로 전환하며 행사 취소와 구분한다.

### 3.2 추천받는 사람

1. 일정 화면에서 가상 계정을 선택한다. 마음 AI 화면의 계정 선택과 같은 React 상태를 사용하지만, 기존 로컬 회원가입 계정과 동일한 계정이라고 가정하지 않는다.
2. `공유된 경조사` 목록에서 행사 유형·제목·기간·지역과 추천 이유를 본다. 행사별 참석 허용은 서버가 먼저 확인한다.
3. 상세를 열 때 서버에 다시 요청한다. 권한이 없어졌거나 소식이 종료됐다면 내용을 지우고 조회할 수 없다는 안내를 표시한다.
4. 목록이 비었을 때와 서버 요청이 실패했을 때를 구별해 안내한다. 계정을 전환하면 이전 계정 목록을 즉시 지우고 이전 요청의 응답은 반영하지 않는다.

이번 단계에서는 목록·상세 조회까지만 제공한다. 개인 일정에 자동 또는 수동으로 복사하지 않고, 개인 장부·참석 여부·금액을 자동 생성하지 않는다. 새 목록에서 AI 상담으로 소식이 선택된 것처럼 이동하는 버튼도 제공하지 않는다.

## 4. 추천 정책

### 4.1 후보와 공개 조건

공통 판정 함수에서 다음 순서로 확인한다. 조건을 하나라도 충족하지 못하면 추천 목록과 수신자 상세 조회에 포함하지 않는다.

1. 소식의 공유자가 본인이 아니고, 양쪽 계정이 존재한다.
2. `friendships.status = accepted`이고 `allow_connection_for_recommendation = true`인 간선만으로 공유자와 직접 연결되거나 두 단계로 연결된다. 요청 대기 관계는 제외한다.
3. 공개 범위가 실제 관계를 허용한다. `private`은 본인 외 제외, `friends_only`는 직접 친구만, `friends_and_friends_of_friends`는 직접 친구와 친구의 친구를 허용한다.
4. 공유 확인이 `confirmed`이고 해당 관계의 참석 허용이 `allowed`다. `unknown`과 `not_allowed`는 제외한다. 직접 친구이면서 공통 친구도 있으면 **직접 친구 조건만** 적용해 참석 불허를 두 단계 경로로 우회하지 못하게 한다.
5. 상태가 예정 또는 진행 중이고 시작일이 종료일을 넘지 않으며, 종료일이 서버의 서울 기준 오늘보다 이전이 아니다. 취소·종료된 소식은 제외한다.

개별 소식 상세도 동일한 판정 함수를 호출한다. 목록에 한 번 나타났다는 사실이나 소식 ID를 알고 있다는 사실만으로 상세 접근을 허용하지 않는다. 소유자가 자신의 새 비공개 소식을 조회하는 경로는 별도로 처리한다.

공개 조건을 통과한 뒤, 수신자가 소유한 서버 가상 개인 행사 중 취소되지 않은 기록의 `shared_occurrence_id`와 소식의 값이 **둘 다 존재하고 정확히 같으면** 이미 등록한 행사로 보고 추천 목록에서만 제외한다. 다른 계정의 개인 행사는 비교하지 않는다. 중복 제외는 공개 권한과 별개이므로 그 이유만으로 기존 상세 접근 권한을 없애지는 않는다. ID가 없거나 이름·제목·날짜만 같은 경우는 자동으로 동일 행사라고 판단하지 않는다.

### 4.2 직장동료 판정

직장동료는 새로운 공개 범위가 아니라, **이미 위 공개 조건을 통과한 소식의 추천 이유**다. 다음을 모두 충족하면 `confirmed_colleague`를 부여한다.

- 수신자가 소유한 서버 가상 인맥의 관계가 명시적인 `직장동료`이고, `linked_user_id`가 소식의 관련 인물 계정과 같다.
- 해당 인맥에 `linked_user_confirmed_for_recommendation = true`가 있다. 기존 레코드에 이 필드가 없으면 `false`다.
- 소식의 `related_user_id`가 공유자 본인이며, 공유자가 관련 인물로서 추천에 사용하도록 허용했고 이름 공개도 허용했다.
- 해당 소식과 관계가 4.1절의 공개·참석 조건을 통과했다.

동일한 이름이나 소속, 브라우저에만 있는 `직장동료` 분류, `linked_user_id`만으로는 연결을 확정하지 않는다. 상주·행사 당사자·공유자를 섞지 않는다. 가상 확인 필드는 실제 신원 또는 제3자의 동의를 검증하지 않는다.

### 4.3 정렬과 표시 이유

추가 점수나 모델 없이 아래 순서로 정렬한다. 여러 이유가 적용되면 가장 높은 범주 하나를 사용한다.

| 우선순위 | 코드 | 표시 예시 |
|---|---|---|
| 1 | `confirmed_colleague` | `확인된 직장동료와 관련된 소식` |
| 2 | `direct_friend` | `직접 연결된 친구가 공유한 소식` |
| 3 | `friend_of_friend` | `친구의 친구가 공유한 소식` |

같은 범주 안에서는 종료일이 빠른 순, 시작일이 빠른 순, 소식 ID 순으로 정렬한다. 특정인 직접 초대 기능은 현재 데이터에 없으므로 순위에 포함하지 않는다. 이 순서는 시연용 가설이며 실제 친밀도·참석 확률이나 추천 정확도를 의미하지 않는다.

공유자의 이름은 해당 소식의 이름 공개가 허용된 때만 표시한다. 공통 친구의 이름과 수는 새 목록에서 표시하지 않는다. 공유자와 관련 인물을 확정할 수 없는 경우 임의의 이름을 만들지 않는다.

## 5. 데이터와 저장 방식

### 5.1 기존 자료

- `data/demo.json`과 그 원천인 `data/original_demo.json`의 기존 레코드를 추천 구현 때문에 직접 수정하거나 삭제하지 않는다.
- 기존 `shared_notices`는 `N...` 또는 `SCN...` ID를 가진 읽기 전용 시연 소식으로 사용한다. 시연 화면에서 이 기존 소식의 편집·철회는 제공하지 않는다.
- `data/scenario_fixtures.json`에 `SCU001`이 소유하고 `SCU006`을 가상 직장동료로 명시적으로 연결한 지인 `SCP019`를 추가한다. 관계는 `직장동료`, 이름은 연결 대상인 `SCU006`의 가상 이름과 일치시키고, 위 연결 확인 필드를 `true`로 둔다. 기존 인맥을 동일인이라고 소급 확정하지 않는다.
- 생성 결과 `data/demo.json`을 갱신해야 한다면 `gyeongjosa_ai/generate_data.py`의 생성 결과를 먼저 별도 임시 위치에서 비교한다. 기존 작업 파일을 확인 없이 `--force`로 덮어쓰지 않는다.
- `tests/test_scenario_dataset.py`의 가상 지인 수 18명과 사용자별 3명 고정 검사는 위 한 건의 추가를 반영한다. 기존 6개 계정·기존 거래·기존 12개 공유 소식과 원본 보존 검사는 유지한다.

### 5.2 새 공유 소식

별도 시연용 SQLite 저장소를 `gyeongjosa_ai/shared_events_store.py`에서 관리하고, 기본 파일은 `data/demo_shared_events.sqlite3`로 둔다. 실행 중 생성되는 해당 DB와 SQLite 보조 파일만 `.gitignore`에 추가한다. 테스트에는 격리된 임시 DB를 주입한다. 기존 대화·프로필 DB는 재사용하거나 삭제하지 않는다.

새 소식의 ID는 기존 시연 ID와 겹치지 않는 `DSE-` 접두사와 UUID로 만든다. 목록 조회 시 읽기 전용 기존 소식과 새 DB 소식을 합쳐 동일한 공개 판정과 정렬을 적용한다. 기존 합성 소식은 DB에 매번 복제하거나 덮어쓰지 않는다.

| 필드 | 내용과 기본값 |
|---|---|
| `id`, `publisher_user_id` | 서버가 생성한 소식 ID와 현재 선택된 가상 계정. 요청 본문에서 공유자 ID를 신뢰하지 않는다. |
| `category`, `title` | 기존 행사 유형인 결혼·장례·백일·돌·생일·환갑·칠순·팔순과 1~100자의 제목. |
| `start_date`, `end_date` | `YYYY-MM-DD`. 실제 날짜여야 하며 시작일은 종료일 이하여야 한다. |
| `region`, `venue` | 선택 입력. 미입력은 `null`로 유지한다. |
| `status` | 새 소식은 `active`로 저장한다. 조회 시 날짜에 따라 예정·진행을 표시하며 취소 상태는 추천하지 않는다. |
| `audience_scope` | `private`, `friends_only`, `friends_and_friends_of_friends`. 기본값은 `private`. |
| `sharing_authorization` | `confirmed` 또는 `unknown`. 공유 범위 저장에는 `confirmed`가 필요하다. |
| `direct_friend_attendance`, `friend_of_friend_attendance` | 각각 `allowed`, `not_allowed`, `unknown`. 기본값은 `unknown`. |
| `publisher_name_visible` | 공유자 이름 공개 허용 여부. 기본값 `false`. |
| `related_user_id`, `related_role`, `related_user_recommendation_allowed` | 관련 인물은 선택 항목이며 P0에서는 공유자 자신만 지정할 수 있다. 역할은 `subject`, `mourner`, `null` 중 하나이고, 추천 활용 기본값은 `false`다. |
| `shared_occurrence_id` | 기존 가상 데이터에 명시된 동일 행사 식별자. 새로 입력한 소식은 이번 단계에서 연결 근거가 없으므로 `null`로 둔다. |
| `created_at`, `updated_at` | 서버가 기록하는 생성·수정 시각. |

기존 부고 데이터와 새 SQLite 데이터의 필드 이름·누락 값은 서버 안에서 같은 내부 형식으로 변환한다. 행사 제목이나 날짜가 같다는 이유로 서로 다른 소식을 자동 병합하지 않는다. 기존 서버 합성 자료에서 `shared_occurrence_id`가 있는 개인 행사와 공유 소식은 각각 일부에 불과하며, 브라우저에 직접 등록한 일정에는 이 연결이 없다. 따라서 이번 단계에서 확인 가능한 ID가 없는 중복은 추천에 남을 수 있다.

`subject`는 장례 외 본인 행사, `mourner`는 본인이 상주인 장례에만 사용한다. 역할이 `null`이면 관련 계정도 `null`이고 관련 인물 추천 활용은 `false`다. 역할이 있으면 서버가 현재 공유자 ID를 관련 계정으로 설정하며, 요청자가 임의의 타인 계정을 넣을 수 없다.

## 6. API 계약

아래 경로는 제안이다. 모든 새 경로는 기존 `_user` 가상 계정 확인을 사용하며, 이는 보안 인증이 아니다. `mine`과 `recommendations`는 `/{id}` 경로보다 먼저 등록해 경로 충돌을 피한다.

| 메서드·경로 | 동작 |
|---|---|
| `GET /api/shared-events/recommendations` | 수신자에게 허용된 기존·새 소식 목록과 서버 기준일을 반환한다. |
| `GET /api/shared-events/mine` | 현재 공유자가 새로 작성한 소식과 공개 상태를 반환한다. 기존 읽기 전용 시연 소식은 편집 대상으로 내놓지 않는다. |
| `GET /api/shared-events/{id}` | 수신자는 4.1절을 다시 통과해야 한다. 새 소식의 작성자는 자신의 비공개 소식도 조회할 수 있다. |
| `POST /api/shared-events` | 현재 가상 계정 명의로 새 소식을 생성한다. 입력·날짜·공개 범위를 검증하고 실패하면 저장하지 않는다. |
| `PATCH /api/shared-events/{id}` | 새 소식의 작성자만 `audience_scope`를 `private`으로 변경해 공유를 철회한다. 다른 사용자와 기존 시연 소식은 수정하지 못한다. |

가상 계정이 없거나 알 수 없으면 `401`, 수신자가 볼 수 없거나 ID가 없으면 공통으로 `404`, 잘못된 입력은 `422`로 응답한다. 목록과 상세 응답에는 허용된 표시 필드만 명시적으로 담고 내부 `publisher_user_id`, `related_user_id`, 공유 판단용 관계 정보는 포함하지 않는다. 작성자의 `mine` 응답도 외부에 보여줄 필요가 없는 내부 ID를 노출하지 않는다.

예를 들어 `SCU006`으로 요청할 때 등록 본문은 다음과 같다. 가상 계정은 기존 `X-Demo-User-Id` 헤더로 전달하며, 공유자와 관련 계정 ID는 본문에 넣지 않는다.

```json
{
  "category": "결혼",
  "title": "한소민의 가상 결혼식",
  "start_date": "2026-11-14",
  "end_date": "2026-11-14",
  "region": "서울",
  "venue": null,
  "audience_scope": "friends_and_friends_of_friends",
  "sharing_authorization": "confirmed",
  "direct_friend_attendance": "allowed",
  "friend_of_friend_attendance": "allowed",
  "publisher_name_visible": true,
  "related_role": "subject",
  "related_user_recommendation_allowed": true
}
```

목록 응답 예시는 다음과 같다. 날짜와 인물은 가상이다.

```json
{
  "demo": true,
  "reference_date": "2026-10-31",
  "items": [
    {
      "id": "DSE-예시",
      "category": "결혼",
      "title": "한소민의 결혼식",
      "start_date": "2026-11-14",
      "end_date": "2026-11-14",
      "region": "서울",
      "publisher_name": "한소민",
      "reason_code": "confirmed_colleague"
    }
  ]
}
```

기존 `/api/notices`, `/api/notices/{id}`, `/api/users/{user_id}/notices`의 부고 전용 동작과 바깥 응답 형태는 유지한다. 단, 이 경로에도 명시적 응답 필터를 적용해 `notice.publisher_user_id` 등 내부 필드는 제거한다. `web/index.html`과 기존 클라이언트가 사용하는 제목·상주·장소 등 허용 필드는 유지하고 회귀 테스트한다. 기존 `ChatService`에는 새 DB 소식을 공급하지 않으며, AI 연동 전까지 새 추천 화면에서 AI 연결을 약속하지 않는다.

1. **기준선과 가상 데이터:** 기존 테스트를 실행하고 `SCP019` 연결을 추가한다. 원본과 기존 소식·거래 보존, 생성 결과의 참조 및 ID 중복 검사를 통과한다.

### 9.1 자동 테스트

| 구분 | 입력·조건 | 기대 결과 |
|---|---|---|
| 직접 친구 결혼 | `SCU001`, `SCN007`, 기준일 `2026-10-30` | 새 목록에 `direct_friend`로 표시한다. 기존 부고 전용 API에는 포함하지 않는다. |
| 친구의 친구 결혼 | `SCU001`, `SCN008`, 같은 기준일 | 새 목록에 `friend_of_friend`로 표시한다. 공유자를 행사 당사자로 단정하지 않는다. |
| 동료 | `SCU006`이 본인 관련 가상 소식을 공유하고 `SCU001`의 `SCP019`가 확인됨 | 이름 공개와 관련 인물 활용이 모두 허용됐을 때만 `confirmed_colleague`를 반환한다. |
| 연결 불명 | 위 동료 사례에서 연결 확인 필드를 제거하거나 관련 인물 사용을 불허 | 동료라고 표시하지 않는다. 나머지 공개 조건을 충족하면 실제 친구 관계 이유만 사용한다. |
| 이름만 같음 | 관련 인물 이름은 같지만 연결된 계정이 없거나 다름 | 동료 판정·개인 이력 자동 연결을 하지 않는다. |
| 공개·참석 | `SCN003`, `SCN004`, `SCN010`, `SCN011`, `SCN012` | 비공개·참석 미확인·공유 미확인 소식은 새 목록과 수신자 상세에서 제외한다. |
| 경로 우회 | 직접 친구 참석은 불허, 친구의 친구 참석은 허용, 공통 친구 존재 | 직접 친구 조건을 적용해 제외한다. |
| 종료·취소 | `SCN005`, `SCN006`, 종료일이 어제인 새 소식 | 모두 제외한다. 종료일이 오늘인 활성 소식은 포함한다. |
| 범위 | `friends_only` 소식을 직접 친구와 두 단계 관계에서 각각 조회 | 직접 친구에게만 허용한다. |
| 이미 등록한 행사 | 접근 가능한 소식과 수신자의 취소되지 않은 서버 개인 행사가 같은 `shared_occurrence_id`를 가짐 | 추천 목록에서만 제외한다. 다른 계정의 개인 행사, 빈 ID, 이름이나 날짜만 같은 행사는 제외 근거로 사용하지 않는다. |
| 철회·소유자 | 작성자가 철회 후 수신자가 목록과 상세를 다시 조회 | 목록에서 빠지고 상세는 `404`다. 작성자는 `mine`에서 비공개 상태를 볼 수 있다. 타 계정의 철회 요청은 허용하지 않는다. |
| 계정과 노출 | 미선택 계정, 존재하지 않는 계정, 이름 비공개 소식 | `401` 또는 허용 정책에 맞는 응답. 새·기존 부고 API에 내부 공유자 ID가 없고 숨긴 이름 값은 반환하지 않는다. 기존 `publisher_name` 필드는 `null`로 유지할 수 있다. |
| 저장·오류 | 새 소식 등록 후 저장소를 다시 열기, 잘못된 날짜, DB 실패 | 재조회 시 저장 내용 유지. 잘못된 입력·저장 실패는 성공으로 표시하지 않는다. |
| 정렬 | 동료·직접 친구·친구의 친구 및 같은 범주 동점 | 4.3절의 범주·종료일·시작일·ID 순서가 재현된다. |
| 기존 상담 | 기존 `N001`, `N002`, 동명이인과 예산 시나리오 | 기존 부고 API의 허용 필드와 `ChatService` 동작을 유지한다. 새 비장례 소식을 부고로 설명하지 않는다. |

테스트의 가상 계정은 임의로 선택 가능한 시연 계정이다. 위 계정별 검사는 정책 분기 확인이며 운영 인증이나 실제 개인정보 보호 성능을 입증하지 않는다.

### 9.2 브라우저 시연

현재 날짜를 기준으로 미래 날짜를 직접 선택한다. 모두 허구의 정보만 사용한다.

1. `SCU006`을 선택하고 본인이 당사자인 가상 결혼 소식을 등록한다. 직접 친구와 친구의 친구 공개, 각 참석 허용, 이름 공개와 관련 인물 추천 활용 허용을 선택한다.
2. `SCU001`로 전환한다. 새 소식이 나타나고 `SCP019` 연결을 근거로 직장동료 이유가 표시되는지 확인한다.
3. `SCU004`로 전환한다. `SCU005`를 거친 친구의 친구 소식으로 표시되고, 직장동료로 단정하지 않는지 확인한다.
4. `SCU003`으로 전환한다. 공유자와 허용된 두 단계 연결이 없어 해당 소식이 나타나지 않는지 확인한다.
5. `SCU006`으로 돌아가 공유를 철회하고 `SCU001`에서 다시 조회한다. 목록에서 사라지고 이전 상세 ID도 조회할 수 없어야 한다.
6. 저장 후 새로 고침해 새 소식과 철회 상태가 유지되는지 확인한다. 기존 개인 일정·장부, 기존 AI 화면과 다른 가상 계정의 추천도 확인한다.

철회는 **다음 서버 조회부터** 반영한다. 이미 화면에 열린 내용을 다른 기기에서 실시간으로 지우는 기능은 이번 단계에 없다. 화면 재진입·새로 고침·탭 복귀 또는 상세 재조회 시 다시 확인하며, 새 추천 데이터를 개인 일정이나 브라우저 알림에 복사하지 않는다.

### 9.3 실행할 검사

- 백엔드: 기존 `onmaeum-integration` 가상환경에서 `python -m pytest -q`와 `python -m unittest discover -s tests -v`.
- 프런트: `frontend`에서 `pnpm test`, `pnpm build`.
- 브라우저: 위 9.2절 시나리오를 실제 실행하고 계정별 결과를 기록한다.
- 임시 폴더 권한으로 pytest가 실패하면 작업 폴더 안의 **새 고유 임시 경로**를 `--basetemp`로 지정해 재실행한다. 이미 존재하는 경로를 재사용하지 않는다.

기준선으로 관련 백엔드 테스트 65개와 기존 프런트 단위 테스트 45개는 이 계획 작성 시 통과했다. 백엔드에는 Starlette 테스트 클라이언트 경고 1건이 있었으며, 전체 테스트·빌드·브라우저 시연은 이번 계획 작성에서 실행하지 않았다.

## 10. 후속 단계와 실서비스 전제

| 단계 | 내용 | 선행 조건 |
|---|---|---|
| P1: 개인 일정 연결 | 사용자가 선택한 추천 소식을 일정에서 참조하고 중복·공유 철회·계정별 저장을 처리한다. | 현재 `localStorage`와 서버 계정의 소유 경계 및 철회 후 표시 정책 결정. |
| P1: AI 연동 | 선택한 공유 소식을 상담에 전달하고 유형별로 내용을 설명한다. | 모든 상담 호출에서 공개 조건 재확인, 관련 인물 확인, 부고 전용 문구·모델 입력 계약 정리. |
| P2: 직장·모임 | 초대와 구성원 자격을 가진 모임에만 소식을 공유한다. | 모임 생성·가입·탈퇴·범위 변경과 접근 통제 설계. 회사 이름이 같다는 이유만으로 같은 모임으로 취급하지 않는다. |
| P2: 외부 소식 | 사용자가 전달한 청첩장·부고 링크 등을 확인 후 가져온다. | 해당 서비스의 연동 기능·이용 조건과 데이터 제공 범위 확인. 자동 수집 가능하다고 가정하지 않는다. |
| 운영 전환 | 실제 인증·인가, 정보주체와 공유 권한 확인, 정보 최소화, 접근 기록, 보관·삭제, 보안과 법률 검토를 수행한다. | 가상 계정·합성 자료 기반 시연을 실제 서비스와 분리. |

실제 이용자가 적거나 공유되는 소식이 없으면 추천도 없을 수 있다. 합성 데이터만으로 추천의 유용성이나 현실의 관계 분포를 입증할 수 없으므로, 운영 전환 시 별도 동의를 받은 평가에서 관련 있는 추천 비율과 누락 사례를 확인한다.

## 1. 요청 범위

1. 회원가입에 **직업·기관·직무·공개 여부**를 추가한다.
2. 인맥 관리의 기존 인맥 추가 기능 옆에 **친구 찾기·받은 요청** 진입점을 추가한다. 친구의 친구를 카드로 추천하고, 요청 수락·거절과 상단 알림함을 연결한다.
3. 실제 회원끼리 연결된 인맥 상세에서만 **연결된 회원**을 표시한다.
4. 챗봇에서 경조사비를 **데이터에 근거해 추천**하도록 현재 구현과 데이터 연결을 점검한다.
5. 사이드바 상단 메뉴의 마지막에 **경조사 예절**을 두고, 하단 기능 메뉴에는 **마음결 AI**만 둔다. 예절 안내 문구도 다듬는다.
6. 작은 글자·터치 영역·접근성·기록 복구·서버 알림·행사 유형·필터 유지·예절 자료 관리를 개선한다.

화면 용어는 최신 요청에 따라 **친구 찾기**로 통일한다. 이전 문서의 표현과 같은 기능이며 별도의 기능으로 만들지 않는다.

## 4. 세부 작업 명세

### R00. 실제 회원 기능을 위한 기반

**필요 작업**

- 서버가 발급하는 불변 `user.id`와 로그인 세션을 기준으로 접근 권한을 검사한다.
- 개인 인맥·장부·일정·알림·설정을 계정별로 분리한다. 클라이언트가 보낸 사용자 ID만 신뢰하지 않는다.
- 회원의 공개 프로필과 사용자가 따로 관리하는 수동 인맥 `Person`을 별도 데이터로 다룬다.
- 기존 체험 계정·샘플·로컬 기록을 실제 계정에 자동 이전하지 않는다. 이전할 데이터와 충돌을 먼저 보여주는 경로를 설계한다.
- 로그아웃·계정 전환 시 진행 중 요청과 이전 계정의 화면·캐시를 정리한다.

**완료 기준**

- [ ] 사용자 A가 B의 인맥·장부·일정·요청을 임의 ID로 조회하거나 수정할 수 없다.
- [ ] 새로고침·재로그인·계정 전환 후에도 데이터 소유권이 유지된다.
- [ ] 서버 저장 실패와 인증 만료가 성공으로 표시되지 않는다.

### R01. 회원가입: 직업·기관·직무·공개 여부

**요청사항**: 기존 가입 항목에 다음 네 항목을 추가한다.

| 항목 | 의미와 입력 예 | 초기 제안 | 결정 필요 |
| --- | --- | --- | --- |
| 직업 | 직업 또는 현재 활동. 예: 회사원·학생·자영업 | 선택 입력. 특정 직업이 없는 경우도 가입 가능 | 직접 입력/선택 목록, 필수 여부, 길이 제한 |
| 기관 | 소속 회사·학교·단체. 예: ○○대학교 | 선택 입력. ‘소속 없음’을 허용 | 공식 기관 검색이 필요한지, 자유 입력인지 |
| 직무 | 담당 업무. 예: 기획·개발·디자인 | 선택 입력. 직업과 기관을 대신하는 값으로 쓰지 않음 | 직무 분류·복수 선택·직책과의 구분 |
| 공개 여부 | 프로필 항목을 다른 회원에게 보여줄 범위 | 기본 비공개 | 공개 대상 항목, 전체 회원/친구 등 범위, 추천 노출 허용과의 관계 |

**구현 시 포함할 내용**

- 화면 입력뿐 아니라 가입 검증·저장·로그인 반환 프로필·프로필 수정까지 같은 계약으로 연결한다.
- 필수값은 화면에서 명시하고 선택 항목을 비워도 정상 처리한다. 앞뒤 공백과 길이 제한을 프런트·서버에서 일치시킨다.
- 새 값이 없는 기존 계정도 로그인할 수 있어야 한다. 누락된 공개값은 비공개로 취급하는 것을 초기안으로 둔다.
- 공개 설정은 서버 응답에도 적용한다. 화면에서 숨기기만 하고 비공개 값을 API로 내려주지 않는다.
- 이름·전화번호·이메일·개인 메모·장부의 공개 여부를 새 프로필 공개값에 암묵적으로 포함하지 않는다.

**완료 기준**

- [ ] 네 항목이 가입·저장·재로그인·수정 후 일관되게 유지된다.
- [ ] 빈 선택 항목, 긴 기관명·직무명, 기존 계정을 정상 처리한다.
- [ ] 공개 범위를 바꾸면 다른 회원의 카드·상세·API 응답에 같은 정책이 적용된다.

### R02. 친구 찾기·친구의 친구 추천·받은 요청

**화면 요구사항**

- 인맥 관리 상단의 기존 인맥 추가 기능 옆에 **친구 찾기**, **받은 요청**을 배치한다. 기존 ‘인맥 등록’ 버튼 명칭을 ‘인맥 추가’로 바꿀지는 화면 정리 시 확정한다.
- 같은 인맥 관리 화면 안에서 친구 찾기와 받은 요청 패널을 전환한다. 모바일에서는 버튼/탭이 겹치지 않도록 배치한다.
- 친구 찾기에는 추천 회원을 **카드**로 표시한다. 카드에는 허용된 이름·프로필과 요청 버튼, 공개가 허용된 추천 이유만 표시한다.
- 받은 요청에는 요청자 정보·수락·거절을 표시한다. 대기 건수와 알림함의 읽지 않은 건수는 의미가 다르므로 구분한다.
- 비로그인·로딩·결과 없음·요청 없음·전송 중·불러오기 실패·이미 처리됨을 각각 안내한다.

**추천 규칙 초기 제안**

1. 수락 완료된 회원 관계에서 공통 친구가 있는 회원을 후보로 찾는다. 수동 인맥에 적힌 ‘친구’ 분류는 추천 그래프에 넣지 않는다.
2. 본인·이미 연결된 회원·요청 대기 중인 상대·탈퇴 회원·추천 노출 비허용 회원을 제외한다. 차단을 제공한다면 양방향 차단 상태도 반영한다.
3. 공통 친구 수를 우선하는 단순 순서로 시작하고, 동점 정렬과 결과 수·페이지 처리를 정의한다. 기관이 같다는 이유만으로 ‘친구의 친구’라고 설명하지 않는다.
4. 공통 친구의 이름·개수도 관계 정보이므로 공개 정책을 정한다. 비공개 관계를 추천 이유로 드러내지 않는다.

**요청·연결 상태**

| 상태/상황 | 화면 동작 | 서버 처리 요구 |
| --- | --- | --- |
| 미연결·요청 없음 | 친구 요청 가능 | 대상·노출·접근 가능 여부 재검사 |
| 요청 대기 `pending` | 요청 중 표시, 중복 제출 방지 | 동일 회원 쌍의 중복 대기 요청 방지 |
| 수락 `accepted` | 실제 연결 상태 표시 | 요청 상태 변경과 양방향 관계 생성을 한 번에 저장 |
| 거절 `rejected` | 연결 배지 미표시 | 재요청 가능 시점은 정책으로 확정 |
| 취소·차단·탈퇴 | 지원 범위에 맞게 요청/연결 불가 안내 | 취소·차단 도입 여부와 데이터 보존 정책 확정 |
| 동시 요청·다른 기기 재처리 | 최신 상태를 보여주고 중복 연결 방지 | 유일성 제약·트랜잭션·재처리 시 일관된 결과 |

**수동 인맥과 회원 연결**

- 수락 후 회원 관계를 생성하는 것과 내 장부의 수동 인맥을 연결하는 것을 구분한다.
- 새 수동 인맥을 만들지, 기존 인맥을 사용자가 직접 선택해 연결할지 결정한다. 이름·이메일 일치만으로 동명이인을 합치지 않는다.
- 인맥 상세의 **연결된 회원** 배지는 서버에 현재 활성 `Friendship`이 존재하고 해당 회원과 명시적으로 매핑된 경우에만 표시한다. 과거 요청의 `accepted` 이력만으로 현재 연결을 판정하지 않는다.
- 연결 해제·탈퇴 후 배지와 공개 프로필을 갱신한다. 연결 여부와 무관하게 개인 장부·메모를 상대방에게 자동 공유하지 않는다.

**기존 상단 알림함 연결**

- 일정 알림과 친구 요청 알림을 `event_reminder` / `friend_request` 등 유형별로 구분한다.
- 새 요청은 요청 ID를 기준으로 중복 없이 알림을 생성한다. 클릭하면 **인맥 관리 → 받은 요청**의 해당 항목으로 이동한다.
- ‘알림 읽음’은 ‘요청 수락’이 아니다. 이미 처리되거나 취소된 요청을 클릭하면 현재 상태를 알려준다.

**완료 기준**

- [ ] A–B, B–C가 연결되고 A–C는 미연결일 때, 공개 정책을 충족하는 C 카드가 A에게 표시된다.
- [ ] A의 요청이 C의 받은 요청과 상단 알림함에 한 번씩 나타난다.
- [ ] 수락 전·거절 후에는 연결 배지가 없고, 수락 및 명시적 인맥 연결 후에만 배지가 표시된다.
- [ ] 반복 클릭·동시 요청·새로고침·다른 기기 재처리로 중복 관계가 생기지 않는다.
- [ ] 다른 사용자의 비공개 프로필·연락처·장부·메모·숨겨진 관계가 카드나 API에 노출되지 않는다.

### R03. 챗봇의 데이터 기반 경조사비 추천

**요청사항**: 챗봇 페이지에서 현재 추천이 어떤 데이터를 사용하는지 점검하고, 실제 기록에 근거한 추천으로 확장한다.

**현재 구현과의 구분**

- 브라우저 모드는 브라우저 기록을 참고하고, 서버 모드는 `MockWorkspaceRepository`의 가상 인맥·가상 장부를 참고한다. 브라우저 기록에도 초기 샘플이 있으므로 실제 입력 기록 여부를 구분해야 한다.
- 현재 추천은 주로 해당 인맥의 최근 받은 금액 또는 같은 행사 유형의 보낸 기록을 참고하는 체험용 규칙이다. 브라우저와 서버의 기록 선택 순서에 차이가 있어 결과가 달라질 수 있으므로 통합 검증이 필요하다.
- 현재 서버의 추천 금액과 근거는 규칙 코드가 만들며, 선택적 LLM은 응답 문장을 작성한다. 모델을 연결하는 것만으로 실데이터 기반 추천이 되지 않는다.
- 현재 챗봇은 인맥을 선택하지만 행사 선택 UI와 `eventId` 전송은 없다. 같은 인맥에게 여러 행사가 있을 때 대상 행사를 선택·확인하는 흐름이 필요하다.
- 현재 응답의 `dataSource: 'mock'`, `demo: true`와 표시용 근거 `{label, value}`는 실데이터 계약이 아니다. 실제 연결 시 클라이언트 검증·서버 스키마·화면 출처 표기를 함께 바꾸고 원본 기록 ID를 추가한다.
- 기존 `/api/ai/advice` 흐름을 확장하는 방향을 우선 검토한다. 기존 연결 명세의 제안 API와 실행 중인 API 경로·스키마를 먼저 대조한다.

**추천 전에 점검할 데이터**

| 확인 항목 | 필요한 처리 |
| --- | --- |
| 소유자·연결 ID | 로그인 사용자와 대상 인맥·행사·장부의 소유권 및 ID를 일치시킨다. |
| 행사·관계 | 행사 유형, 상대와의 관계, 참석 여부 등 사용한 조건을 명시한다. 없는 조건을 추정해 채우지 않는다. |
| 금액 기록 | 보낸 금액과 받은 금액을 구분하고 날짜·유형·거래 방향을 함께 조회한다. |
| 데이터 품질 | 중복 가져오기·삭제 기록·잘못된 금액·미래 날짜·오래된 기록·표본 부족의 처리 기준을 정한다. |
| 출처 | 샘플·사용자 입력·서버 저장 기록을 구분하고, 서로 다른 계정의 기록을 합치지 않는다. |

**추천 방식 초기 제안**

1. 본인이 해당 인맥과 주고받은 기록을 먼저 확인한다.
2. 필요하면 본인의 같은 행사 유형·비슷한 관계 기록을 보조 근거로 사용한다. 어떤 조건과 기간으로 골랐는지 공개한다.
3. 중앙값 등 재현 가능한 계산으로 기준값 또는 범위를 만든다. 최소 표본 수·기간·이상치·반올림·가중치는 구현 전 정책표로 확정한다.
4. 데이터가 부족하면 그 사실과 빠진 정보를 먼저 알린다. 근거 없는 기본 금액을 ‘데이터 추천’으로 제시하지 않는다.
5. AI는 계산 결과를 설명하고 추가 질문을 돕는다. 금액과 근거 기록을 새로 만들어내거나 계산 결과를 임의로 바꾸지 않는다.

기관·직업·직무만으로 경제력이나 적정 금액을 추정하지 않는다. 다른 회원의 비공개 장부나 친구 관계를 추천 근거로 쓰지 않는다. 외부 통계·시세를 추가하려면 자료 출처·시점·이용 범위와 개인 기록과의 구분을 별도 설계한다.

**챗봇에 보여줄 결과**

- 추천 금액 또는 범위. 산출 불가이면 금액을 생략한다.
- 사용한 기록 건수·기간·행사 유형·관계 조건과 확인 가능한 근거.
- 데이터 출처, 기준 시각, 계산 규칙 버전. 가상데이터는 가상데이터라고 표시한다.
- 받은 금액이 추천에 미친 영향, 제외한 데이터와 정보 부족 사유.
- ‘기록을 참고한 제안이며 최종 금액은 직접 결정한다’는 짧은 안내.
- 서버 대기·취소·재시도·연결 실패 상태. 홈의 내장 AI와 챗봇 페이지가 같은 근거와 계산을 사용하도록 맞춘다.

**완료 기준**

- [ ] 같은 기록·조건·규칙 버전에는 같은 금액 결과가 나오며 근거로 재현할 수 있다.
- [ ] 기록 없음·같은 유형 기록 없음·다른 유형만 존재·중복·극단값·미래 날짜·오래된 기록·주고받은 방향 혼합을 검증한다.
- [ ] 샘플과 사용자 기록, 브라우저와 서버 출처가 화면에서 구분된다.
- [ ] 장부 수정·삭제 후 추천과 통계가 같은 최신 데이터를 참조한다. 다른 계정 기록은 조회할 수 없다.
- [ ] 모델이 실제 근거에 없는 거래·금액·‘일반적인 시세’를 사실처럼 출력하지 않는다.
- [ ] 서버 계산 금액·화면 금액·AI 본문의 숫자가 일치한다. 실패를 가짜 금액이나 성공한 모의 응답으로 대체하지 않는다.
- [ ] 같은 인맥/행사/기록에 대한 브라우저와 서버 규칙을 일치시킨다. 의도적인 차이는 출처와 함께 설명한다.
- [ ] 인맥·행사 선택 변경과 요청 취소 후, 이전 응답이 새로운 선택에 섞이지 않는다.

### R04. 사이드바 재배치와 예절 문구 다듬기

**요청을 반영한 배치안**

```text
상단 메뉴
  홈
  일정 관리
  인맥 관리
  금액 · 통계
  경조사 예절   ← 상단 메뉴의 마지막

하단 기능 메뉴
  마음결 AI       ← 하단 기능 메뉴에는 AI만 배치
```

- 접힌 사이드바·펼친 사이드바·모바일 메뉴에 같은 그룹과 순서를 적용한다.
- 경로와 선택 표시, 키보드 이동, 기존 홈·일정 상세의 AI 진입을 유지한다.
- 낮은 화면 높이에서 상단 메뉴와 하단 AI가 겹치지 않게 한다. 하단 장식 문구 유지 여부는 레이아웃 검토 때 결정한다.

**예절 문구 편집 원칙**

- 짧고 구체적인 행동을 먼저 쓰고, 경사에는 축하·조사에는 차분한 위로의 말투를 사용한다.
- 가족·지역·종교·현장 안내를 우선한다. 하나의 의례나 금액을 모두에게 맞는 정답으로 단정하지 않는다.
- 행사별로 ‘가기 전 / 현장에서 / 전할 말 / 배려할 점’의 구조를 맞춘다.
- AI 생성 문구와 검토한 고정 안내를 구분한다. 출처 검토는 R11에서 관리한다.

**바로 편집에 사용할 문구 초안 — 최종 확정 전**

| 위치 | 문구 초안 |
| --- | --- |
| 페이지 소개 | 마음을 전할 때 필요한 준비와 인사말을 살펴보세요. |
| 공통 안내 | 예절은 가족·지역·종교에 따라 달라질 수 있어요. 초대한 분과 현장의 안내를 먼저 따라 주세요. |
| 금액 안내 | 축의금과 조의금에 하나의 정답은 없어요. 관계와 내 형편을 함께 살펴 결정해 주세요. |
| 조문 안내 | 짧고 정중하게 위로를 전하고, 유족에게 답장을 재촉하지 않아요. |
| 참석이 어려울 때 | 함께하기 어렵다면 미리 연락해 축하나 위로의 마음을 전해 보세요. |
| 일정 상세 연결 | 이 행사에 맞는 예절 보기 |

**완료 기준**

- [ ] 모든 사이드바 상태에서 상단 마지막은 예절, 하단 기능 메뉴는 AI로 표시된다.
- [ ] 예절 내용이 행사 맥락과 맞고, 중복되거나 강압적인 표현이 줄어든다.
- [ ] 메뉴의 포커스·선택 표시·모바일 닫기·AI 진입이 유지된다.

### R05. 글자 크기와 가독성

- 홈·AI·통계·CSV·알림의 7~10px 보조 문구를 목록화하고, **읽어야 하는 본문·보조 설명은 14~16px 수준**을 목표로 확대한다. 의미 없는 장식까지 일괄 확대하는 방식은 피한다.
- 충분한 행간을 확보한다. 초기 제안은 본문 `1.5~1.7`이며 실제 한글 문장과 화면으로 확인한다.
- 카드 높이·버튼·표·입력칸을 함께 조정한다. 홈의 높이에 맞추기 위해 중요한 설명을 숨기거나 글자를 다시 줄이지 않는다.
- 200% 확대, 320/360px 너비의 작은 모바일, 긴 이름·기관명·행사 제목·금액·오류 문장을 점검한다.

**완료 기준**: 필수 정보가 잘리거나 겹치지 않고, 주요 동작에 접근할 수 있다. 표가 가로 스크롤을 사용하면 스크롤 가능함과 관리 버튼 접근 경로를 알 수 있다.

### R06. 터치 영역·상태 표시·접근성

- 삭제·수정·닫기·월 이동·탭·필터의 실제 터치 영역을 **44×44 CSS px 안팎**으로 확보하는 것을 목표로 한다. 아이콘 그림과 누르는 영역은 구분한다.
- 선택·오류·읽음·연결·요청 상태를 색상 외에 글자·아이콘·선택 상태 속성으로도 전달한다.
- 키보드 순서와 눈에 보이는 포커스, 모달 진입·닫기 후 포커스 복귀, 탭 전환과 버튼 이름을 점검한다.
- 밝은/차분한 테마 모두 글자·배경·아이콘·포커스 대비를 측정한다. 배포 전 적용할 접근성 기준과 버전을 정해 수치와 결과를 기록한다.
- 자동 검사와 함께 실제 키보드·스크린리더로 회원가입·친구 요청·기록 수정/삭제·챗봇을 사용해 본다.

**완료 기준**: 마우스 없이 주요 흐름을 완료하고, 아이콘만 있는 버튼과 상태 변경을 스크린리더로 이해할 수 있다. 확인한 도구·환경·남은 문제를 검수 기록에 남긴다.

### R07. 삭제 복구·변경 이력·가져오기 보호

- 현재 삭제 확인 이후의 영구 제거를 개선한다. 초기안은 **즉시 실행 취소 + 일정 기간 복구함**이며, 적용 대상과 기간을 먼저 정한다.
- 장부를 우선 적용 대상으로 검토하고 일정·인맥까지의 범위는 별도로 확정한다. 삭제·복구 시 연결 정보와 통계·추천의 포함 여부를 일치시킨다.
- 서버 저장 실패 시 원래 기록 또는 미저장 입력으로 돌아갈 수 있게 한다. 중복 클릭·네트워크 재시도·동시 수정도 처리한다.
- 생성·수정·삭제·복구의 주체·시간·변경 내용을 계정별 이력으로 관리한다. 변경 이력을 일반 사용자가 수정할 수 없도록 한다.
- CSV 가져오기 전에 백업 방법과 추가/중복 제외 범위를 안내한다. 가져오기 원본과 미리보기는 실패 후 다시 확인할 수 있게 한다.
- 현재 CSV는 **금액 기록 내보내기**이며 계정 전체 백업은 아니다. 전체 복구를 제공한다면 인맥·일정·연결 ID까지 포함한 별도 형식과 복원 절차가 필요하다.
- 내보내기는 ‘현재 계정의 조회 결과 / 현재 계정의 전체 금액 기록’ 등 실제 범위를 명확히 표시한다.

**완료 기준**: 삭제 후 새로고침·재로그인해도 정책에 맞게 복구할 수 있고, 복구 전후 장부·인맥 이력·통계·추천이 일치한다. 실패한 가져오기가 일부 데이터만 저장하는 상태를 만들지 않는다.

### R08. 서버 예약 알림·Web Push·발송 이력

- 서버 예약 작업, 서비스 워커, 계정별 기기 구독, 푸시 발송과 결과 기록을 설계한다. 현재 페이지의 `new Notification()`만으로 앱 종료 후 알림을 구현했다고 간주하지 않는다.
- 기본 시간대는 현재 앱과 같은 `Asia/Seoul`을 제안한다. 알림 시각·당일/며칠 전·조용한 시간·놓친 알림 처리·기기별 발송 정책을 정한다.
- 일정 생성·수정·삭제 시 예약을 생성·변경·취소하고, 이전 일정 버전의 작업이 뒤늦게 발송되지 않게 한다.
- 계정·대상·알림 유형·예약 회차·기기/채널을 구분하는 중복 방지 키를 설계한다. 재시도·여러 작업자·여러 기기에서 정책대로 처리한다.
- 구독 만료·권한 거부·전송 실패·로그아웃·계정 변경 시 동작을 정하고, 설정에 테스트 알림 발송을 제공한다.
- 상단 알림함과 Web Push는 같은 사건을 참조하되 별도 전달 상태를 가진다. 서버 전송 성공을 사용자의 실제 열람으로 표시하지 않는다.
- 친구 요청을 Web Push로도 보낼지, 잠금화면에 요청자 이름 등 어느 정보를 표시할지는 별도 확정한다.

**완료 기준**: 지원 브라우저/기기에서 페이지를 닫은 상태의 수신을 확인하고, 일정 변경·취소·재시도·조용한 시간·구독 만료·로그아웃을 검증한다. 운영체제와 브라우저의 전달 제한도 검수 결과에 기록한다.

### R09. 행사 유형·음력·반복 일정

- 일정 등록의 결혼식·장례식·돌잔치·생일과 예절의 어른 생신·아기 축하 분류가 다르다. 저장용 행사 유형과 안내용 분류를 분리해 매핑한다.
- 환갑·칠순·팔순을 ‘어른 생신’ 아래 세부 유형으로 둘지, 설정에서 유형을 확장할지 결정한다.
- 유형 추가 시 달력·필터·장부·통계·CSV·알림·AI·예절 링크를 함께 점검한다. 기존 기록을 임의로 재분류하지 않는다.
- 음력은 윤달·변환 출처/라이브러리·대상 연도 범위·오류 처리, 반복은 매년/매월·해당 날짜 없음·2월 29일·종료 조건을 먼저 정의한다.
- 반복 일정 수정/삭제는 ‘이번 일정만 / 이후 일정 / 전체’의 범위를 결정하고, 이미 기록된 금액과 과거 일정이 바뀌지 않게 한다.

**완료 기준**: 정의한 경계 날짜 사례를 통과하고, 같은 행사 유형이 등록·조회·추천·내보내기에서 일관되게 처리된다.

### R10. 필터·정렬 유지와 빈 화면 안내

- 인맥·장부·일정의 검색·필터·정렬·선택 월 중 무엇을 유지할지 정한다. 초기안은 같은 계정의 화면 재방문 시 마지막 상태를 복원하는 것이다.
- 새로고침·다른 기기까지 유지할지, URL/세션/계정 설정 중 어디에 저장할지 별도로 결정한다. 계정 전환 시 이전 계정의 검색어나 결과를 노출하지 않는다.
- 이미 있는 인맥 검색 지우기·달력의 오늘 기능은 유지한다. 다른 화면에도 검색 지우기·필터 초기화의 의미와 위치를 맞춘다.
- ‘데이터가 없음’, ‘검색 결과가 없음’, ‘필터에 맞는 결과가 없음’, ‘불러오기 실패’를 구분하고 인맥 추가·일정 등록·검색 초기화·다시 시도 등 다음 행동을 제공한다.

**완료 기준**: 화면을 나갔다 돌아와도 결정한 상태가 복원되고, 초기화/오늘 복귀가 예측대로 동작한다. 다른 계정의 상태가 섞이지 않는다.

### R11. 예절 콘텐츠 관리와 일정 상세 연결

- 예절 항목에 자료 출처·검토일·편집 담당·변경 이력을 관리한다. 실제 확인하지 않은 날짜를 검토일로 기록하지 않는다.
- 기존 출처 링크의 접근 가능 여부와 안내 내용이 인용 취지에 맞는지 다시 확인한다. 단순 편집 의견과 출처가 뒷받침하는 내용을 구분한다.
- 일정 상세에 **이 행사에 맞는 예절 보기**를 추가하고 해당 유형으로 이동한다. 닫기/뒤로가기 시 기존 일정으로 돌아올 수 있게 한다.
- 알 수 없는 유형은 전체 예절로 안내하고, R09의 유형 확장과 매핑을 함께 관리한다.

**완료 기준**: 결혼식·장례식·아기 축하·어른 생신의 연결 대상이 맞고, 검토 정보와 출처를 확인할 수 있다. AI 문장을 검토 완료된 고정 지침처럼 표시하지 않는다.

## 5. 데이터·API 계약 초안

아래 이름은 **설계 초안**이다. 실제 스키마·경로·저장소를 그대로 확정한 것이 아니다. 기존 `BACKEND_INTEGRATION.md`와 실행 중인 FastAPI 계약을 대조한 뒤 한 곳에서 관리한다.

| 데이터 | 역할 | 주요 항목 예 |
| --- | --- | --- |
| MemberProfile | 회원의 공유 가능한 프로필 | `userId`, `occupation`, `organization`, `jobRole`, `profileVisibility`, 추천 노출 설정 |
| Person | 내가 관리하는 개인 인맥 | `id`, `ownerId`, `linkedMemberId?`, 관계·메모. 회원 공개 프로필과 분리 |
| FriendRequest | 회원 간 연결 요청 | `id`, `senderId`, `receiverId`, `status`, 생성·처리 시각 |
| Friendship | 현재 활성 회원 관계 | 정규화한 회원 쌍, 생성 시각. 활성 관계는 같은 쌍에 하나만 존재. 해제 시 삭제/비활성화 정책은 결정 필요 |
| Notification | 사용자별 알림함 항목 | `id`, `recipientId`, `type`, `targetId`, `readAt`, `createdAt` |
| RecommendationEvidence | 금액 추천 계산의 근거 | 소유자, 기록 ID, 표본 수·기간, 기준 시각, 규칙 버전, 산출 상태 |
| Recovery/Audit | 복구와 변경 추적 | 대상·소유자·작업·주체·시각·이전/이후 값, 만료 정책 |

**필요한 API 기능 목록**

- 프로필 조회·수정과 공개 범위 적용.
- 회원 추천 조회, 받은 요청 조회, 요청 전송·수락·거절. 취소·차단·연결 해제의 포함 여부는 확정 후 추가.
- 알림 목록·읽음 처리·유형별 이동 대상. 친구 요청과 알림 생성의 일관성 보장.
- 사용자 소유 장부를 조회하는 AI 근거 생성과 기존 `/api/ai/advice` 응답 확장.
- 삭제·복구·변경 이력·백업/복원과 예약 알림·기기 구독 관리.

전체 API에 서버 권한 검사·입력 검증·오류 코드·페이지 처리·동시성 정책을 적용한다. 요청/저장 재시도가 필요한 작업에는 중복 저장을 막는 정책을 정한다.

## 6. 구현 전에 결정할 항목

정책이 필요한 작업만 확인을 기다리고, 독립적인 화면·스타일 작업은 병행할 수 있다.

- [ ] **프로필**: 세 입력의 필수 여부·입력 방식·길이 제한, 공개 대상 항목, 기본 공개값, 공개 범위.
- [ ] **발견 가능성**: 프로필 공개와 추천 노출을 같은 설정으로 둘지, 별도 동의/설정으로 둘지.
- [ ] **친구 정책**: 추천 이유 공개 범위, 요청 취소·재요청·차단·연결 해제, 요청 유효기간.
- [ ] **인맥 연결**: 수락 시 수동 인맥을 새로 만들지, 사용자가 기존 인맥을 명시적으로 선택할지.
- [ ] **금액 추천**: 비교 기간·관계 분류·최소 표본 수·계산법·이상치·반올림·정보 부족 시 응답. 예산 입력을 추가할지.
- [ ] **복구**: 적용 대상·보관 기간·영구 삭제·변경 이력 보관·백업 형식.
- [ ] **알림**: 시각·조용한 시간·장례식 등 예외·재시도·미발송 처리·기기별 발송·잠금화면 노출 범위.
- [ ] **일정**: 유형 확장 방식·음력/윤달·반복·과거 일정 보존 정책.
- [ ] **필터·콘텐츠**: 상태 유지 범위, 로그아웃 처리, 예절 편집 담당과 검토 주기.

## 7. 권장 작업 단위와 진행 순서

1. **정책·계약 정리**: R01~R03의 미확정 사항과 R00의 회원/소유권 모델을 정한다. 필요한 데이터·API 계약을 문서에 반영한다.
2. **독립 화면 개선**: R04 사이드바·예절 문구, R05 글자, R06 입력/포커스, R10 기존 동작의 일관성을 작은 변경 단위로 진행한다.
3. **회원 기반 연결**: R00 인증·계정 데이터, R01 가입/프로필 저장·공개 정책을 연결한다.
4. **친구 요청부터 구현**: R02 요청·수락/거절·인맥 매핑·상단 알림을 구현한 뒤 친구의 친구 추천을 연결한다.
5. **실데이터 금액 추천**: R03의 출처·계산·근거 계약을 연결하고 브라우저/서버/샘플 구분을 검증한다.
6. **기록과 알림 신뢰성**: R07 복구·이력·가져오기 보호, R08 서버 예약과 Web Push를 구현한다. 서버 CRUD 단계부터 복구용 필드를 고려한다.
7. **유형과 콘텐츠 확장**: R09 날짜 정책과 R11 예절 연결·검토 관리를 적용한다.
8. **통합 검수**: 두 회원 계정·서로 다른 기기/세션·작은 모바일·200% 확대·키보드·스크린리더로 핵심 시나리오를 검증한다.

각 단위는 변경 파일·데이터 영향·검증 결과를 남긴다. 계획 문서만 작성된 상태를 기능 완료로 표시하지 않는다.
